# 目标计划助手 · 需求计划书

- 版本：v1.1（功能需求 + UI 定稿）
- 日期：2026-10-14
- 用途：本文档是**自包含**的需求说明，可直接交给他人或别的 AI 阅读，用于界面实现与继续开发
- 状态：功能需求已定；**界面设计已定稿**（见第 10 节）

---

## 1. 产品一句话

在聊天里对话收集需求 → 生成专属方案 → 用户确认 → 自动落成「目标 + 按天计划」；日常按天打卡，每周复盘；数据全在本地，模型用用户自己的 API Key。

**形态**：Windows 桌面应用（Tauri），单机、单用户、纯本地存储。

---

## 2. 用户与场景

- **用户**：只有一个人用（作者自己）。没有账号、没有多用户、没有云同步。
- **使用节奏**：每天打开一次，几十秒；每周坐下来写一次复盘；偶尔通过聊天改方案。
- **典型目标**：30 天减脂、21 天读完一本书、30 天每天写 300 字。
- **成功标准**：连续用满 14 天，且第 8 天还愿意打开。（这是判断"做成了没有"的唯一标准）

---

## 3. 核心机制（不理解这三条，就不能理解这个产品）

### 3.1 草案 → 确认 → 版本

- 聊天里产生的一切默认都是**草案**，不生效、可随时丢弃。
- 用户点「确认」后，草案才变成**正式版本**并生效。
- 一个目标同时最多只有一个生效版本；确认新版本时，旧版本自动归档。
- 归档版本**只读**，但它的打卡记录**原样保留**（可回看，不迁移、不清空）。
- 版本状态只有三个：`draft`（草案）→ `active`（生效）→ `archived`（归档）。

### 3.2 收集需求是一个状态机，不是自由聊天

- 会话有阶段：`collecting`（收集）→ `drafting`（生成）→ `confirmed`（已确认）。
- 收集阶段按固定字段清单逐个提问，字段集齐才允许生成方案。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 目标类型 | 是 | 减脂 / 学习 / 写作 等 |
| 目标描述 | 是 | 一句话说清想达成什么 |
| 周期与起止日 | 是 | 例如 30 天，从哪天开始 |
| 当前基线 | 是 | 现在是什么水平，否则无法对比 |
| 可用时间/频次 | 否 | 每天能投入多少 |
| 限制与禁忌 | 否 | 伤病、忌口、设备限制 |
| 偏好 | 否 | 喜欢的运动 / 学习方式 |
| 成功标准 | 否 | 怎么算成功 |

### 3.3 方案必须是结构化数据，不是自由文本

- 模型以 **JSON** 返回方案（字段对应第 5 节的数据模型）。
- 本地做严格校验：天数与起止日是否吻合、日期是否连续、序号是否从 1 连续递增、必填是否为空。
- 校验失败 → 把具体错误回传模型重试，**最多 2 次**。
- 仍失败 → 降级为纯文本回复，并明确告知"方案未保存"，**绝不写入脏数据**。

## 4. 功能需求

### 4.1 聊天

- 对接大模型（默认 DeepSeek，OpenAI 兼容协议）。
- 逐字流式输出；生成中可「停止」，未完成的消息标记为"未完成"，可重新生成。
- 聊天记录保留在本地便于回看；但**真正生效的只有确认过的方案**。
- 断网时：聊天不可用，给出可行动的提示（不是"出错了"），其余功能全部照常可用。

### 4.2 目标

- 目标列表 + 详情；数量不限制。
- 目标可归档（**不支持删除**，避免误删打卡历史）。
- 新建目标的唯一入口是「确认一份草案」，不提供手工建空目标。

### 4.3 计划（按天）

- 一个计划由 N 天组成，每天有：序号、日期、标题、说明、可选的若干任务项。
- 计划属于某个版本，版本属于某个目标。
- 改方案的方式：**基于当前生效版本 + 用户新需求，生成一份全新草案**，确认后替换（MVP 不做局部 diff 修改）。

### 4.4 打卡

- 动作只有一个：勾选某一天"完成"。不强制记录任何数据（不填时长、不填重量）。
- 规则：
  - 只能给**生效版本**打卡（草案和归档版本都不行）
  - 只能给**今天及以前**的日期打卡；未来日期拒绝
  - 只能给**该版本范围内**的日期打卡；超出范围拒绝
  - 同一天不能重复打卡
  - 任何一次拒绝都要给出具体原因，不能静默失败
- 允许**补打**（补过去漏掉的日子），也允许**取消**（可逆）。
- 破坏性操作（如清空数据）必须先自动备份。

### 4.5 周复盘

- 按自然周（周一到周日）切分，可前后翻周。
- 两种模式都要：
  - **手写**：自由文本，保存后一直可回看
  - **模型总结**：取本周计划 + 打卡记录，生成草稿文本，**可再编辑后保存**
- 触发方式：纯手动按钮，不自动跑。
- 首周不满七天时，只统计计划开始之后的那几天。

### 4.6 设置（产品级，不是某个目标的设置）

设置是**整个应用**的，与当前在哪个目标无关。分组如下：

1. **模型与密钥**：API Key、模型名、接口地址。温度和语气写死（稳健、友好、简短），暂不开放调节。
2. **提醒**：每日打卡提醒、周复盘提醒、计划开始提醒，各带时间。**默认为关**（原因见 8.1）。
3. **数据与备份**：自动备份开关、保留份数、立即备份、导出全部数据、从备份导入、清空数据。
4. **主题**：外观（浅色/深色/跟随系统）、文字大小。另建议包含每周起始日（周一/周日，影响周复盘怎么切）和"关闭窗口时的行为"（每次询问/最小化到托盘/直接退出）。
5. **关于**：版本号、数据文件位置、清空聊天记录。

### 4.7 导出与恢复

- 导出内容：数据库文件 + 一份可读 JSON 快照 + 一份版本说明（含 schema 版本、导出时间、记录条数）。
- 导入：先自动备份当前数据 → 校验版本兼容 → 事务替换。
- **API Key 不进导出**（换机器要重新填）。
- 导出和导入必须成对实现，只有导出没有导入的备份没有意义。

## 5. 数据模型

SQLite。关键约束写在表里。

**goal**：id、title、description、status（active/archived）、created_at、updated_at

**plan_version**：id、goal_id、version_no（同一目标内从 1 递增）、status（draft/active/archived）、source（chat/manual）、summary、start_date、end_date、created_at、activated_at
- 约束：`UNIQUE(goal_id, version_no)`；**部分唯一索引保证一个目标只有一个 active**

**plan_day**：id、plan_version_id、day_index（1..N）、date（YYYY-MM-DD）、title、detail、tasks（JSON）、is_rest
- 约束：`UNIQUE(plan_version_id, day_index)`

**check_in**：id、plan_day_id、date、done_at、note
- 约束：`UNIQUE(plan_day_id)`（一天最多一条打卡）

**review**：id、goal_id、plan_version_id、week_start（周一）、mode（manual/ai）、content、created_at
- 约束：`UNIQUE(goal_id, plan_version_id, week_start, mode)`

**chat_session**：id、goal_id（可为空）、title、stage（collecting/drafting/confirmed）、collected（JSON）、created_at

**chat_message**：id、session_id、role（user/assistant/system）、content、status（complete/interrupted/failed）、created_at

**setting**：key、value（**只存非敏感值**；API Key 不进这里）

**schema_migration**：version、applied_at

### 5.1 关键不变量（任何实现都不能违反）

1. 一个目标同时最多一个 `active` 版本。
2. 归档版本只读；它的打卡保留且可查看。
3. 打卡只存在于生效版本的日期上，且日期 ≤ 今天。
4. 「确认」是单个事务：旧 active 归档 → 草案转正 → 写 activated_at。
5. 草案与正式版本同表，靠 status 区分，不设独立的草案表。

## 6. 失败与离线

| 情形 | 判定方式 | 提示 | 行为 |
| --- | --- | --- | --- |
| 无网络 | 连接失败 | 网络不可用，目标与计划仍可查看 | 保留已输入内容，给重试 |
| Key 无效 | 401 / 403 | API Key 无效，请到设置检查 | 一键跳设置页 |
| 限流 | 429 | 请求过于频繁，稍后重试 | 退避后自动重试 1 次 |
| 超时 | 60 秒 | 响应超时 | 给重试按钮 |
| 服务异常 | 5xx | 服务暂时不可用 | 给重试按钮 |
| 结构不符 | JSON 校验失败 | 不打扰用户 | 带校验错误重试 ≤ 2 次，再降级为纯文本且不入库 |
| 流式中断 | SSE 提前结束 | 这条回复未完成 | 标记为未完成，可重新生成 |

**总原则**：网络问题绝不阻塞本地功能。断网时可以看目标、计划、打卡、复盘，也可以打卡和写复盘。

## 7. 技术约束

| 项 | 约束 | 原因 |
| --- | --- | --- |
| 外壳 | Tauri 2（不建议 Electron） | 安装包要小 |
| 前端 | React + TypeScript + Vite | 生态成熟 |
| 后端 | Rust，所有数据库访问收口在 Rust 命令层 | 离线/在线边界可控 |
| 数据库 | SQLite（rusqlite，bundled 编译） | 单文件、零配置、便于备份 |
| 网络 | reqwest + rustls | 不依赖系统 OpenSSL，避免打包踩坑 |
| Key 存储 | Windows 凭据管理器（或 DPAPI 加密），不进数据库、不进前端 | 安全 |
| 包体目标 | ≤ 10 MB（不含 WebView2 运行时） | 硬约束 |
| 禁用 | 不嵌 Node / Python sidecar | 会让包体涨几十 MB |
| 依赖 | WebView2 Runtime（Win11 与多数 Win10 已内置） | 首次启动要检查 |
| 运行 | Windows 10/11 桌面，鼠标键盘；不需要移动端 | 自用 |
| 界面语言 | 中文，单语言 | 自用 |
| 时间 | 时间戳统一存 UTC 整数，界面按本地时区显示 | 避免跨时区错乱 |
| 日期 | 本地日期字符串 `YYYY-MM-DD`；周固定周一到周日 | 打卡与周复盘都依赖它 |

**字体注意**：如果界面要用衬线中文字体（例如思源宋体），中文全字库 5～8 MB，必须做子集化，否则会顶穿包体目标。这是设计阶段就要知道的一条硬约束。

### 8.1 「提醒」的特殊说明

提醒原本列在"不做"里，后来被放进设置面板。需要明确的是：

- **界面部分很便宜**（几个开关加时间选择）
- **实现部分不便宜**：要拿系统通知权限；而且"应用没开着也要能提醒"在 Windows 上需要常驻托盘进程或系统计划任务，会直接影响包体与资源占用
- **当前决定**：设置里保留位置，默认关闭，MVP 不接实现

## 10. UI 定稿

界面已定稿。实现必须遵守本节布局、主题与交互；不得擅自改成浅色工具风或其它主题，除非另行改版。

### 10.1 视觉主题：赛博霓虹

| 项 | 定稿 |
| --- | --- |
| 名称 | 赛博霓虹（深色霓虹） |
| 气质 | 深色、夜城、粉青霓虹强调；有主题感，但不抢打卡主操作 |
| 背景 | 近黑 / 深灰蓝（约 `#0A0A0F`～`#0F172A`）；可有极淡雨夜城市虚化，不可喧宾夺主 |
| 侧栏 | 近黑；选中项青霓虹描边或弱发光 |
| 强调色 | 青（`#22D3EE` 一类）+ 粉品红（`#F472B6` 一类）；主按钮可用青→粉渐变 |
| 卡片 | 深色半透明玻璃感；细霓虹描边；圆角约 12px |
| 字体 | 系统中文无衬线；不用思源宋等大字库 |
| 深浅色 | MVP **只做深色主题**（本主题即默认）；暂不提供浅色切换 |
| 包体 | 主题靠 CSS 色板与少量装饰，不嵌大尺寸背景图包进安装包；若用背景图须压缩且可关 |

### 10.2 壳与导航

- 窗口最小：1280 × 720；Windows 桌面，鼠标键盘
- 左侧竖导航约 200px，**仅三项**：**目标**、**聊天**；**设置**固定在侧栏底部
- **不设**一级导航「计划」「打卡」「总览」等（详情内部承载）
- 点进某个目标后，主区为「目标详情」；顶栏：目标名 + 版本状态（如 `v2 生效`）+ 次要入口「周复盘」「改方案」

### 10.3 各屏布局

**目标列表**

- 页标题「我的目标」
- 每条：名称、进度文案（如「完成 6 / 共 14 天」）、右侧状态「今天未打 / 今天已打」（未打偏粉提示，已打偏青）
- 点整行进详情

**目标详情（主战场 · 今天优先）**

1. **上半屏大卡「今天」**：日期 + 第 N 天 · 大标题 · 说明 · 主按钮「完成今天」（已完成则变为弱样式「取消打卡」）
2. **一条进度**：第几天 / 完成 / 漏 / 剩 + 细进度条（无统计图表）
3. **下半可滚**：
   - 「漏打」：过去未完成日 +「补打」
   - 「接下来」：未来日只读预览（不可打卡）
4. 归档版本：整页只读，无打卡按钮
5. 周复盘、改方案：从顶栏进入（子页 / 切到聊天）

**聊天**

- 消息流 + 底栏输入；生成中可「停止」
- 草案卡：标签「草案」+ 摘要 +「确认生效」+「改一改」
- 视觉上明确区分草案与已生效

**周复盘（子页）**

- 自然周翻周；本周打卡摘要；手写保存 / 模型生成草稿后再编辑保存

**设置**

- 五个分组见 4.6；提醒分组为占位，默认关，MVP 不接实现

### 10.4 交互契约（不可违反）

- 打卡一次点击完成，可取消；不强制填数据
- 未来日期不可打卡，拒绝须给具体原因
- 归档版本只读；草案不能打卡
- 同一目标仅一个生效版本；界面「当前方案」必须指向它
- 「确认」为不可逆事务（只能再生成新版替换）
- 断网：聊天顶条提示「网络不可用，本地功能仍可用」；其余照常

### 10.5 设计张力的定稿取舍

| 张力 | 定稿 |
| --- | --- |
| 今天优先 vs 全景 | **今天优先**；全景用下半滚动解决 |
| 聊天与计划空间 | **分离**：日常打卡在详情；改方案进聊天 |
| 进度表达 | 仅用天数类极简指标，不做统计图 |

### 10.6 原型参考

定稿气质以对话中确认的「赛博霓虹」三屏原型为准（目标列表 / 目标详情 / 聊天）。实现时对齐色板与层级，不要求像素级复刻插画背景。

## 11. 术语表

| 术语 | 含义 |
| --- | --- |
| 目标 | 用户想达成的一件事，例如"减脂 30 天" |
| 方案 / 计划 | 一份按天拆开的执行安排，属于某个目标的某个版本 |
| 版本 | 一份方案的一次落库。有草案、生效、归档三种状态 |
| 草案 | 模型生成但用户还没确认的方案，不生效 |
| 确认 | 用户把草案转为生效版本的动作，是不可逆事务 |
| 归档 | 旧版本在确认新版本后进入的只读状态，打卡保留 |
| 打卡 | 把某一天标记为"完成"，一次点击，可取消 |
| 补打 | 给今天以前的、漏掉的日子补上打卡 |
| 收集 | 模型按固定字段清单向用户提问的阶段 |
| 周复盘 | 每周一次的文字总结，可手写，也可让模型根据打卡生成草稿 |
